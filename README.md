# nm-automata

NetworkManager bindings for Rust, generated in full from NetworkManager's own spec.

Every interface, every enumeration, every connection-profile property — 53 proxies, 113 types
and 530 settings properties, with upstream's documentation attached — produced by machine from
what NetworkManager publishes, and regenerated when it releases. Nothing is transcribed by
hand, so nothing is half-covered and nothing drifts.

```rust
use nm_automata::{DeviceState, NetworkManagerProxy};

let connection = zbus::Connection::system().await?;
let nm = NetworkManagerProxy::new(&connection).await?;

for device in nm.get_devices().await? {
    if device.state().await? == DeviceState::Activated {
        println!("{} is up", device.interface().await?);
    }
}
```

`just example` prints every device, its type, state and capabilities.

## What is generated

Everything under `nm-automata/src/generated/` — 53 proxies, 113 enumerations and flag sets, and
their documentation — comes from what NetworkManager publishes, pinned to the release in
`spec/nm-version.txt`:

| In `spec/` | Gives | How |
| --- | --- | --- |
| `introspection/*.xml` | the interfaces, and the gtk-doc documentation in their comments | fetched from the git tag |
| `NM-1.0.gir` | every enumeration and flag set, with values and documentation | built (`just build-spec`) |
| `nm-settings-docs-dbus.xml` | connection-profile properties and their D-Bus types | built (`just build-spec`) |

No C source is parsed. The first is fetched straight from the git tag and diffs against
upstream; the other two only exist once NetworkManager has been compiled, so a container does
that and the results are committed — see [How generation works](#how-generation-works).

Nothing is transcribed by hand. The hand-written Rust is `src/repr.rs` (two macros defining how
a NetworkManager type is put on the wire), `src/ext.rs` (three traits for turning object paths
into proxies) and `src/settings.rs` (the plumbing the generated profile structs are built on) —
about 400 lines in total.

### Every profile property is an `Option`

NetworkManager normalises a profile before it validates it, so an absent property means "decide
for me" and a present one means "use exactly this" — and the two are different. Left unset,
`connection.autoconnect-retries` consults the global default; set to `0` it means *forever*.
Filling in the documented defaults would quietly change what a written profile means.

Only `connection.id` and one base-type setting are genuinely required — `uuid` is generated by
NetworkManager when absent and `type` is inferred from whichever base setting is present.
`ConnectionProfile::new` supplies the first. Settings and properties this binding does not know
are kept in `other` maps, so a read-modify-write against a newer daemon does not drop them.

## What that buys over raw proxies

* **Types instead of integers.** `device.state()` returns `DeviceState`, not `u32`;
  `device.capabilities()` returns a `bitflags` set. NetworkManager documents which properties
  and arguments are which, and generation reads that — then checks it against the D-Bus
  signature, so a documentation slip cannot produce a binding that fails to decode.
* **Forward compatibility.** Enumerations decode unknown values to `Other(n)` and flag sets
  keep unknown bits, so a crate built against one release still works against a newer daemon.
  The example above was generated from 1.58.0 and runs against 1.56.1.
* **Upstream's documentation, as rustdoc.** NetworkManager keeps its docs in XML comments,
  which plain introspection tooling drops. Generation lifts them back out and puts them on the
  proxies, their methods, and every argument.
* **Members that return object paths return the objects.** `get_devices()` gives
  `Vec<DeviceProxy>`, `device.active_connection()` gives an `ActiveProxy` — built on the
  connection the proxy already holds, so nothing has to be passed in:

  ```rust
  for device in nm.get_devices().await? {
      if let Some(active) = device.active_connection().await? {
          println!("{:?}", active.state().await?);
      }
  }
  ```

  A property pointing at no object — an unassociated Wi-Fi device's `ActiveAccessPoint`, a
  device with no addresses yet — is `None` rather than a proxy that fails on first use.
  NetworkManager says it with `/`, which no object of any interface is ever at, so this is the
  one nullability the binding decides for you; `NULL_PATH`, `is_null()` and `non_null()` are
  there when you are holding the path itself.

  Going the other way, every proxy knows its own path — `device.object_path()` gives a
  `DevicePath`, which is what the members that take one expect. The raw members are still there
  under a `_path`/`_paths` name (`get_device_paths`); they are rarely what you want, but a
  property's change stream is named after them, so watching `ActiveConnection` means
  `receive_active_connection_path_changed`. 44 of the 45 path-valued properties are typed either
  way; the one left is `Connection.Active.SpecificObject`, which really is an access point *or* a
  Wi-Fi P2P peer.
* **Narrowing a device is checked, not a cast.** `device.specialise()` reads the type once and
  returns an `AnyDevice`, whose variants each carry a proxy that could only have been built
  after the matching type was seen:

  ```rust
  match device.specialise().await? {
      AnyDevice::Wireless(wifi) => wifi.get_access_points().await?,
      AnyDevice::Wired(wired) => { wired.speed().await?; vec![] }
      other => { println!("{:?}", other.device_type()); vec![] }
  }
  ```

  `ProxyExt::cast` is still there for the interfaces every object of a kind carries —
  `Device.Statistics` is on every device — but it is unchecked and documented as such.
* **The dictionaries are structs too.** `ip4.address_data()` gives `Vec<AddressData>` with
  `address` and `prefix` fields, not a map of variants; likewise routes and the resolver
  configuration. These four shapes are the one place NetworkManager describes its keys only in
  prose, so they are written down in `annotations.toml` — safe to do because every one of them
  is a read-only property, where a mistake is a decode error rather than a corrupted profile.
  `Device.LldpNeighbors` is deliberately left as a map: it maps LLDP TLV names to values and
  has no fixed shape.
* **Signals carry objects too.** `receive_access_point_added()` yields `AccessPointProxy`, not a
  path, so a new access point can be asked what it is straight away:

  ```rust
  while let Some(access_point) = seen.next().await {
      println!("{:?}", access_point?.ssid().await?);
  }
  ```

  `cargo run --example watch` shows it against real scan activity. Property changes come
  straight from zbus: `receive_state_changed()` for the property stream,
  `receive_state_changed_signal()` for the signal of the same name.
* **Connection profiles are structs, not `a{sa{sv}}`.** All 530 properties across 57 settings
  have real fields — `profile.wireless.ssid`, `profile.ipv4.method` — with upstream's
  documentation on each, and the proxies speak them directly:

  ```rust
  fn get_settings(&self) -> zbus::Result<ConnectionProfile>;
  fn update(&self, properties: &ConnectionProfile) -> zbus::Result<()>;
  ```

  Every property and setting also has a setter of its own name, so building one does not mean
  writing `Some` at each field — the structs stay plain, so a literal with
  `..Default::default()` still works just as well:

  ```rust
  let profile = ConnectionProfile::new("home wifi").wireless(
      WirelessSetting::default()
          .ssid("my-network")
          .mode(WirelessMode::Infrastructure),
  );
  ```

  `cargo run --example profiles` reads every profile on the machine through both the typed and
  the raw path and reports any property that differs.
* **A profile property is typed as what it means, not as what it travels as.** A property whose
  values are a fixed set of strings is an enumeration of them — `Ipv4Method::Auto` and
  `WirelessMode::Infrastructure`, not `"auto"` and `"infrastructure"` — and NetworkManager
  declares most of those sets as constants, so they are read out of the spec like everything
  else; the handful it documents only in prose
  (`802-11-wireless.band`, the Wi-Fi security ciphers) are in `annotations.toml`, checked
  against the settings table. An SSID is an `Ssid` rather than a `Vec<u8>`, since 802.11 defines
  it as octets and not as text — `AccessPoint.Ssid` on the proxy side too, since it is the same
  string — and a hardware address is a `MacAddress` that reads and writes `4C:79:6E:DA:29:47`.
  `assigned-mac-address` holds either an address or a word asking NetworkManager to pick one, so
  it is an enum with both: `AssignedMacAddress::Random`, or `Address(MacAddress)`. None of this
  changes the wire: a value the binding does not know is kept as it came and written back
  unchanged, so a read-modify-write never rewrites a profile.

## Keeping up with upstream

Tasks are [`just`](https://just.systems) recipes; `just --list` shows them all.

```
just latest-version   # newest stable NetworkManager release
just fetch            # vendor the introspection XML (just fetch 1.56.1 to pin one)
just build-spec       # build the generated inputs in a container (slow, needs podman)
just generate         # regenerate nm-automata/src/generated/
just update           # all three, in one step
just check            # fail if the checked-in output is stale
just regen            # generate, format, and run everything CI runs
just clean            # drop this crate's build artifacts, keeping compiled dependencies
```

`.github/workflows/update-spec.yml` runs `just update` weekly, verifies the result with
`just ci`, and opens a pull request. The diff under `nm-automata/src/generated/` *is* the API
change, so a NetworkManager release is reviewed as a normal PR rather than chased by hand.
`.github/workflows/ci.yml` runs `just check` on every push, so the generator and its output
cannot drift apart.

## How generation works

`zbus_xmlgen` writes the proxies, but NetworkManager's introspection XML on its own would only
produce integers and undocumented methods. The generator in `codegen/` bridges that gap:

1. `codegen/src/gir.rs` reads `NM-1.0.gir`: every `<enumeration>` and `<bitfield>`, with values
   and documentation already resolved by the introspection scanner.
2. `codegen/src/annotate.rs` recovers the type references and documentation from the XML
   comments — `Returns: NMDeviceState`, `@managed: (NMDeviceManaged) …`.
3. `codegen/src/render.rs` writes both back into the XML as Telepathy `tp:` annotations, which
   `zbus_xmlgen` does understand, and emits the types as `nm_enum!`/`nm_flags!` invocations.
4. `codegen/src/codegen.rs` runs the generator per interface and assembles the result.

It stays a Rust crate rather than becoming shell recipes because it uses `zbus_xml` and
`zbus_xmlgen` as libraries; `just` is what invokes it.

### Why two of the three inputs are built rather than fetched

The types of enumerations and of connection-profile properties are not machine-readable
anywhere in NetworkManager's git tree — they come from GObject introspection data, which only
exists once libnm has been compiled. `just build-spec` compiles it at the pinned tag in a
container and runs NetworkManager's own generators. `ninja` is asked for one target, so the
daemon is never linked.

That cost lands only on whoever bumps the vendored release, which is already the moment a human
reviews a regeneration. The artifacts are committed, so building `nm-automata` as a dependency needs
no container, no C toolchain and no GLib.

The settings documentation is *not* derived from the introspection data alone, even though it
could be: NetworkManager merges it with the `---dbus---` comment blocks in its sources, because
about thirty properties travel as something other than their GObject type — `ipv4.dns` is an
array of strings to GObject and an array of packed integers on the wire, and every MAC address
is a string to GObject and a byte array on D-Bus. Taking NetworkManager's merged answer avoids
having to reconcile that, and getting it wrong would corrupt profiles rather than fail loudly.

The augmented XML is written to `target/nm-automata-augmented/` on every run, so what the generator
was fed is always inspectable.

Two details worth knowing:

* NetworkManager gives some interfaces a `State` property *and* a `StateChanged` signal, or a
  `Managed` property *and* a `SetManaged` method. Both want the same Rust name. The property
  keeps it; the other becomes `receive_state_changed_signal()` or `set_managed_method()`.
* Interfaces get one module each, because `Settings.Connection` and `VPN.Connection` both
  generate a `ConnectionProxy`. Names that are unique across the spec are re-exported at the
  crate root as they are; the rest keep their module's name in front —
  `SettingsConnectionProxy`, `VpnConnectionProxy`.

`annotations.toml` fills in the few members whose type upstream does not state in a form worth
inferring from — `Device.IPTunnel.Mode` is documented as "The tunneling mode." and nothing more.
Entries there are checked against the vendored spec, so one that stops applying fails generation
instead of rotting.

There are no signature tests against the spec. Everything on both sides of such a check comes
from the same vendored files and is regenerated together, so it would only ever restate what
generation just did; `just check` re-runs generation and diffs the result, which is the same
guard done properly.

## Features

```toml
# async-io, the default
nm-automata = "0.1"

# tokio instead
nm-automata = { version = "0.1", default-features = false, features = ["tokio"] }
```

### Using it with tokio

`async-io` and `tokio` select the runtime zbus drives its connection with, and one of them is
required. Turning defaults off is the part that matters — adding `tokio` on its own leaves
`async-io` enabled as well, and zbus gates on `tokio`, so you would get tokio anyway with
async-io compiled in and unused.

Nothing else changes. Build the connection inside your runtime as usual:

```rust
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let connection = zbus::Connection::system().await?;
    let nm = nm_automata::NetworkManagerProxy::new(&connection).await?;

    for device in nm.get_devices().await? {
        println!("{}", device.interface().await?);
    }
    Ok(())
}
```

The examples run either way, which is how this is checked:

```
cargo run --example devices                                            # async-io
cargo run --example devices --no-default-features --features tokio     # tokio
```

Enabling both is permitted rather than rejected, since cargo unifies features additively and two
crates in one dependency tree may each ask for a different runtime — a hard error here would
break graphs that zbus itself handles. With neither, zbus fails to compile with its own
`compile_error!` before this crate is reached.

`blocking-api` additionally generates the blocking proxies.

## Empty strings

D-Bus has no null, so a property with no value still has to send something, and many of
NetworkManager's send `""` — a device with no permanent hardware address, or a Wi-Fi P2P device
asked for its `HwAddress`. `NonEmpty` reads that as absent where you know that is the meaning:

```rust
use nm_automata::NonEmpty;

match wireless.perm_hw_address().await?.non_empty() {
    Some(address) => println!("permanent address {address}"),
    None => println!("no permanent address"),
}
```

The getters themselves keep returning what NetworkManager sent, because nothing upstream says
which properties mean it — the introspection XML has no nullability annotation, and the GIR
marks no property nullable. Guessing would also be wrong often: an empty `connection.permissions`
grants *every* user access, and an empty `802-1x.altsubject-matches` disables certificate
verification. Reading either as "unset" inverts it.
